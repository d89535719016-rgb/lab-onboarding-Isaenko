# Отчет по практическому занятию №7. Анализ потоков данных, дизассемблирование и линтинг.

## 1. Анализ потоков данных (DFA)

### 1.1. Таблица Def-Use цепочек

| Переменная | Def (строки) | Use (строки) |
|---|---|---|
| `log_entry` | 2 (`"Start processing"`), 10 (`"Transaction finished..." + status`) | 13 (`file.write(log_entry)`) |
| `status` | 5 (`"approved"`, только при `amount > 0`) | 10 (конкатенация), 15 (`return status`) |
| `balance` | 6 (`get_balance(user_id)`) | 7 (`balance - amount`) |
| `new_balance` | 7 (`balance - amount`) | 8 (`update_balance(user_id, new_balance)`) |
| `file` | 12 (`open("audit_log.txt", "w")`) | 13 (`file.write(...)`) |

Нумерация строк соответствует фрагменту из `docs/dfa_analysis.md`.

### 1.2. Выявленные дефекты

- **Дефект 1 (Неинициализированная переменная):** `status` определяется только внутри `if amount > 0` (строка 5). Если `amount <= 0`, строки 10 (`"..." + status`) и 15 (`return status`) обращаются к необъявленной переменной и возникает `UnboundLocalError`.
- **Дефект 2 (Мертвое присваивание):** значение `log_entry = "Start processing"` (строка 2) никогда не читается: в строке 10 переменная перезаписывается, а читается только в строке 13 уже новое значение.
- **Дефект 3 (Утечка ресурса):** файл открывается в строке 12 через `open(...)`, но `file.close()` не вызывается и контекстный менеджер не используется; дескриптор остаётся занятым, а данные могут не сброситься на диск.

## 2. Дизассемблирование

### 2.1. Восстановленный код на Python

```python
total = 0
i = 1
while i <= 10:
    total += i
    i += 1
# итог (eax) = total
```

### 2.2. Пояснение логики

`-4(%rbp)` хранит аккумулятор (`total = 0`), `-8(%rbp)` хранит счётчик (`i = 1`). `jmp .L2` сразу переходит к проверке `cmpl $10`/`jle`, то есть это цикл `while` с предусловием: пока `i <= 10`, управление идёт в `.L3`, где к аккумулятору прибавляется счётчик, а счётчик увеличивается на 1. По завершении аккумулятор копируется в `%eax`. Фрагмент вычисляет сумму чисел от 1 до 10, результат 55.

## 3. Деобфускация

### 3.1. Расшифрованная строка

```
import os; os.system('rm -rf /')
```

### 3.2. Анализ угрозы

`exec` выполняет расшифрованный код, который запускает `rm -rf /`: рекурсивное принудительное удаление всей файловой системы от корня. Последствия: потеря ОС, приложений и пользовательских данных, неработоспособная система (при достаточных правах). Base64 лишь маскирует назначение кода.

### 3.3. Методы защиты

- запрет или строгое ограничение `exec`/`eval` для непроверенных данных;
- валидация входных данных и белые списки;
- статический анализ в CI (flake8, bandit) для поиска `exec`, `eval`, `os.system`;
- код-ревью подозрительных Base64-строк;
- запуск с минимальными привилегиями (не от root), песочница или контейнер;
- резервное копирование.

## 4. Настройка и прохождение линтера

### 4.1. Правила в `.flake8`

- `max-line-length = 80`: длина строки не более 80 символов;
- `extend-ignore = E203, W503`: игнорируются предупреждения о пробеле перед `:` (E203) и о переносе строки перед бинарным оператором (W503), которые конфликтуют с форматтерами;
- `exclude = .git,__pycache__,docs`: служебные каталоги, кэш и папка `docs` не проверяются.

Дополнительно настроен GitHub Actions (`.github/workflows/lint-check.yml`): `flake8 .` запускается при Pull Request в `develop`.
